## 验证结果与边界

本机 Node.js 22.16.0、Python 3.14.5。33 个 Node 测试、7 个 Python 解析测试通过；数据库结构及文件关系检查通过。

本机未发现可用 MariaDB/MySQL 服务，Docker 引擎未启动；npm 离线安装返回 ENOTCACHED。因此改用 PR 内的隔离 MariaDB 与构建环境完成上述 API、并发和编译验证。本机静态预览端口也无法从浏览器连通；未宣称已人工完成整套购票 UI、摄像头扫码或所有后台按钮验收。

`Project checks` 在验证提交上四个任务全部成功：静态检查、用户端构建、管理端构建、票务验收。票务任务使用独立 MariaDB 10.11，只导入 `ticketing_ac`；现有 AC 17/17、补充数据库/API 六组检查、WebSocket 8/8 全部通过，并已上传 `.cache/checks/` 证据。最终核对另外修正了迟到退款审计描述，并在服务回归中断言“门票与座位保持不变”；最终提交继续运行相同的完整 CI。

## 仍需优化

1. **P1：零价票的业务规则。** 管理端和订单表允许 0 元；payment_attempts.amount 与 refunds.amount 要求大于 0。当前零元订单不能沿用普通付款流程。应明确免费票是否需要支持，并实现免费出票流程或在管理端及 API 一致拒绝零价票。
2. **P2：完整托管部署。** API 及 WebSocket 目前仅允许本机来源。配置外部管理员页面地址并不等于外部 API 可用；需统一 HTTPS、API 基址和精确来源白名单。
3. **P2：异常退款失败后的重试。** FAILED 为终态，迟到付款仍保留待退款标记，但尚无独立的再次出款流程；对账只能记录状态。
4. **P2：购票端语言支持。** 公开看板与管理端提供三种语言；购票端仍以英文为主。
5. **P3：快照与反馈。** 演示座位数据不会跟随 CAP 每 12 小时同步；应继续明确快照时间，并考虑购票端搜索竞态、请求失败重试和更完整的无障碍实测。
